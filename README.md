# Shop Triage

[![CI/CD](https://github.com/SergeyLT/shop-ai-triage/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/SergeyLT/shop-ai-triage/actions/workflows/ci.yml?query=branch%3Amain)

API для первичной обработки обращений интернет-магазина. Сервис определяет тему обращения, готовит черновик ответа и помечает случаи, требующие участия оператора. Черновик возвращается вызывающей системе; сервис не отправляет сообщения покупателям.

## Возможности

- `POST /triage` принимает текст обращения, канал и идентификатор клиента.
- Модель `openai/gpt-6-luna` вызывается через ProxyAPI. Результат проверяется по контракту; при ошибке возвращается безопасный шаблон с эскалацией.
- История принятых обращений и результатов хранится в SQLite. Отдельный ключ защищает API, лимиты действуют по клиенту и на сервис в целом. Расход токенов учитывается по обращениям и ограничивается суточным бюджетом.
- `GET /health` сообщает готовность приложения и версию образа. Диагностические JSON-логи не содержат текст обращений и ключи.

## Стек и устройство

| Задача | Технология |
|---|---|
| HTTP API и валидация | Python 3.12, FastAPI, Pydantic |
| Обработка текста | ProxyAPI, `openai/gpt-6-luna` |
| Аудит и лимиты | SQLite |
| Запуск и поставка | Docker Compose, GitHub Actions, GHCR, Coolify |
| Диагностика | JSON в stdout; сбор через Docker и внешнюю систему логов |

HTTP-слой передаёт нормализованное обращение в обработчик. Обработчик получает ответ модели, проверяет его и при необходимости включает эскалацию. После этого результат записывается в SQLite и возвращается вызывающей стороне.

Входной контракт (`text`, `channel`, `client_id`) позволяет принимать обращения от разных источников: магазина, онлайн-сервиса и других систем. Сейчас промпт, правила категорий и проверочные примеры настроены для интернет-магазина. Для другого сценария можно сохранить API и основную обработку, адаптировав промпт и набор проверок под его обращения. Если нужны другие категории или правила эскалации, потребуется также обновить контракт ответа и соответствующую логику. Подключение конкретного источника выполняет внешний адаптер; готовых интеграций с почтой, мессенджерами или CRM в сервисе нет.

## API

`POST /triage` принимает JSON:

```json
{
  "text": "Заказ оплачен, но статус не обновился. Что делать?",
  "channel": "form",
  "client_id": "demo-client-1"
}
```

`text` обязателен и содержит от 1 до 2000 символов; `channel` — `email`, `form` или `chat`; `client_id` — непустой идентификатор длиной до 128 символов. Используйте непрозрачный `client_id` вместо адреса почты или телефона. Передавайте ключ приложения в заголовке `X-API-Key`. Пример ответа:

```json
{
  "category": "billing",
  "draft_reply": "Укажите, пожалуйста, номер заказа и сведения о платеже, чтобы можно было проверить оплату.",
  "confidence": "high",
  "escalate": true
}
```

Категории: `billing` — платежи и возвраты; `support` — заказ, доставка и технические вопросы; `complaint` — жалобы на товар или обслуживание; `other` — остальные темы. Уверенность: `high`, `medium`, `low`; это качественная оценка категории и следующего шага, а не статистическая вероятность. При `low` эскалация обязательна. `escalate=true` означает, что обращение требует участия оператора сейчас; простой уточняющий вопрос может получить `false`. В текущем промпте отсутствие чека после оплаты и неизвестное наличие товара считаются поводами для эскалации. Ответ содержит черновик из 1–6 предложений. Неверный ключ даёт HTTP 401, ошибочный JSON или поля — HTTP 422, превышение минутного лимита запросов — HTTP 429. При ошибке хранилища сервис отвечает HTTP 503. При ошибке модели или исчерпании суточного бюджета токенов API сохраняет обращение и возвращает категорию `other`, низкую уверенность, `escalate=true` и шаблон «Обращение требует проверки оператором». Сервис сам не направляет обращение оператору.

Интерактивная схема API доступна по `/docs`. `/health` не требует ключа.

## Контроль расхода модели

`PROXYAPI_MAX_COMPLETION_TOKENS` ограничивает один ответ модели (по умолчанию 1200), `DAILY_TOKEN_BUDGET` — общий бюджет приложения за сутки UTC (по умолчанию 20 000). Перед вызовом сервис резервирует консервативную оценку расхода, чтобы одновременные запросы не обходили бюджет. После ответа резерв заменяется значением `usage` от провайдера; если провайдер не сообщил расход, резерв остаётся учтённым. Это ограничение вызовов внутри приложения, а не денежный лимит аккаунта ProxyAPI.

SQLite хранит входные, выходные и общие токены по каждому обращению, когда провайдер их сообщает. Посмотреть текущий бюджет можно внутри запущенного контейнера:

```sh
docker compose exec api python -m shop_triage.budget
```

Обе настройки задаются в `.env` локально или в переменных Coolify для production. Минутные лимиты `RATE_LIMIT_PER_CLIENT` и `RATE_LIMIT_GLOBAL` остаются отдельной защитой от частых запросов.

## Данные и диагностика

В локальном Compose и Coolify база SQLite хранится в постоянном томе `triage-data` по пути `/data/tickets.sqlite3` внутри контейнера. Команда `docker compose down` сохраняет том. Посмотреть последние записи аудита в локальном контейнере можно так:

```sh
docker compose exec api python -m shop_triage.audit
```

Приложение пишет по одной JSON-строке на событие в stdout. В каталоге локального проекта последние записи и непрерывный поток можно посмотреть так:

```sh
docker compose logs --tail=100 api
docker compose logs -f api
```

Заголовок ответа `X-Request-ID` позволяет найти события одного запроса. В развёрнутом экземпляре логи доступны через Coolify и Grafana; в них нет текста обращения и черновика ответа. Для резервной копии работающей SQLite используйте команду из раздела развёртывания, а не копирование одного файла базы при включённом WAL.

Импортируемый [дашборд логов Grafana](observability/grafana/README.md) помогает найти события по `X-Request-ID` и показать итог обработки, HTTP-результат и ошибки.

## Запуск через Docker на Windows

Нужны Docker Desktop с Docker Compose и ключ ProxyAPI. В PowerShell из корня репозитория:

```powershell
docker run --rm python:3.12-slim python -c 'import secrets; print(secrets.token_urlsafe(48))'
Copy-Item .env.example .env
notepad .env
docker compose build
docker compose up -d
Invoke-RestMethod http://localhost:8000/health
```

Первая команда выводит случайный ключ для `TRIAGE_API_KEY`; вставьте его в `.env`. Значение `PROXYAPI_API_KEY` возьмите из ProxyAPI. Для модели `openai/gpt-6-luna` оставьте `PROXYAPI_TEMPERATURE=none`: модель принимает только значение по умолчанию. Для проверки обработки:

```powershell
$apiKey = Read-Host 'Введите TRIAGE_API_KEY из .env'
$body = @{ text = 'Заказ оплачен, но статус не обновился'; channel = 'form'; client_id = 'demo-client-1' } | ConvertTo-Json
Invoke-RestMethod -Uri http://localhost:8000/triage -Method Post -Headers @{ 'X-API-Key' = $apiKey } -ContentType 'application/json; charset=utf-8' -Body $body
docker compose exec api python -m shop_triage.audit
```

## Запуск через Docker на Linux

Нужны Docker Engine с Docker Compose и ключ ProxyAPI. В командной строке из корня репозитория:

```bash
docker run --rm python:3.12-slim python -c 'import secrets; print(secrets.token_urlsafe(48))'
cp .env.example .env
${EDITOR:-vi} .env
docker compose build
docker compose up -d
curl -fsS http://127.0.0.1:8000/health
```

В `.env` задайте `TRIAGE_API_KEY` из вывода первой команды и свой `PROXYAPI_API_KEY`. Для проверки обработки и записи в SQLite:

```bash
read -rsp 'Введите TRIAGE_API_KEY из .env: ' API_KEY; echo
curl -fsS http://127.0.0.1:8000/triage \
  -H 'Content-Type: application/json' \
  -H "X-API-Key: $API_KEY" \
  --data '{"text":"Заказ оплачен, но статус не обновился","channel":"form","client_id":"demo-client-1"}'
docker compose exec api python -m shop_triage.audit
unset API_KEY
```

`docker compose down` останавливает сервис и сохраняет том с SQLite. Для отдельного проверочного запуска на том же VPS задайте в `.env` другой `HOST_PORT`, например `8001`, и используйте отдельное имя Compose-проекта: `docker compose -p shop-triage-check up -d --build`. Так проверка получит собственный том и не затронет экземпляр в Coolify.

## Развёртывание через Coolify

Production использует готовый образ из GHCR и [compose.coolify.yml](compose.coolify.yml). GitHub Actions проверяет код и собирает образ на pull request без публикации. После успешных проверок push в `main` публикует `latest` и SHA-тег, вызывает deploy webhook Coolify и ожидает, пока `/health` покажет новый SHA.

1. Создайте в Coolify Docker Compose-приложение по файлу `compose.coolify.yml`. Укажите `GHCR_IMAGE` в виде `ghcr.io/<владелец>/<репозиторий>` строчными буквами. Для приватного образа настройте доступ Coolify к GHCR только на чтение.
2. Задайте в Coolify разные значения `TRIAGE_API_KEY` и `PROXYAPI_API_KEY`. Остальные настройки имеют значения по умолчанию в Compose и могут быть изменены через окружение. Подключите домен с HTTPS и постоянный том `triage-data`.
3. Отключите автоматический деплой из Git в Coolify: запуск будет приходить из GitHub Actions. В настройках приложения Coolify откройте Configuration → Webhooks и скопируйте **Deploy Webhook (auth required)** вида `https://<адрес-coolify>/api/v1/deploy?uuid=<uuid>&force=false`. Создайте API-токен Coolify с правом Deploy. Webhook событий GitHub из раздела Manual Git Webhooks для этого workflow не подходит.
4. В GitHub задайте секреты `COOLIFY_WEBHOOK` (скопированный адрес) и `COOLIFY_TOKEN` (API-токен). В `PUBLIC_BASE_URL` укажите внешний HTTPS-адрес приложения через прокси Coolify: без `/health` и без внутреннего порта контейнера `8000` (например, `https://shop-triage.example.com`). Workflow проверяет тип webhook и отправляет `POST` для запуска деплоя. После push в `main` проверьте результат workflow и версию в `/health`.

SQLite рассчитана на один экземпляр приложения. Перед обновлением схемы или удалением тома создайте согласованную резервную копию через `python -m shop_triage.backup /data/backups/<имя>.sqlite3` внутри контейнера и перенесите файл в отдельное хранилище. Для отката используйте неизменяемый SHA-тег предыдущего рабочего образа.

## Проверки

Обычные тесты подменяют модель и не делают платных вызовов ProxyAPI. Для разработки установите пакет с группой `dev` в `.venv`, затем выполните `ruff check .`, `ruff format --check .`, `mypy src` и `pytest` через интерпретатор окружения. CI выполняет эти проверки автоматически. Реальный вызов модели проверяется отдельно с собственным ключом.

Для проверки смыслового качества есть [набор из 20 обращений](evals/README.md), [заполненный чек и результаты](evals/report.md). Живой прогон запускается только вручную и расходует токены; в CI он не входит. Набор помогает находить конкретные ошибки промпта, но не заменяет оценку на реальных обезличенных обращениях.
